## RESOLVED: Energy measurement: support mixed\_\* Hamiltonian operators

**Status:** Fixed (Python measurement layer)

Added general `mixed_*` operator evaluation to `_energy.py`. Decomposition strategy:

- Parse `mixed_T_S1_S2_...` notation (time order + spatial orders per axis)
- Resolve time derivatives: order 0 → field, order 1 → velocity, order 2 → acceleration from EOM RHS
- For constraint fields: differentiate constraint equation (velocity sources → acceleration, field sources → velocity/acceleration)
- Apply spatial gradients sequentially after time resolution
- Wired into `_evaluate_hamiltonian_factor` dispatch for seamless integration

Also added `mixed_*` to operator validation in `json_loader.py`.

**Complementary Wolfram IBP optimization** (not yet implemented): Integration by parts on the Lagrangian before the Legendre transform could reduce mixed operators at the source. The Python handler is the primary mechanism; IBP is an optimization for cleaner JSON

## OPEN: Pre-decomposition reduction for faster GW derivation

**Status:** Open (optimization)
**Priority:** Low
**Labels:** enhancement, performance

Benchmark (2026-02-28) of GW plane-wave derivation (18 min total):

- xPert + VarD: 0.4 sec (0%) -- abstract symbolic phases are fast
- DecomposeToComponents: 469 sec (42%) -- converts abstract EOM to 10 component equations
- DecomposeScalarExpression (canonical): 634 sec (57%) -- Hamiltonian decomposition

**Pre-linearization reduction is NOT worth it** since xPert+VarD take <1 sec.

**Actual optimization:** Per-component early exit in `DecomposeToComponents`. After `ToBasis` but before expensive `Expand`, zero transverse Derivative patterns. If the component is identically zero, skip remaining steps. For GW with plane-wave reduction, 8 of 10 components would short-circuit, potentially saving ~80% of decomposition time.

Requires modifying `ComponentDecompose.wl` (`ExtractTensorComponent`) and `DecomposeScalarExpression`. Both are shared infrastructure requiring careful testing.

See `memory/pre-linearization-benchmark.md` for full analysis.

## OPEN: SuperLU memory failure on moderate grids — sparse tier gap

**Status:** Open (bug / architecture)
**Priority:** Medium
**Labels:** bug, solver, performance

**Problem:** IDA's sparse tier (2K < N ≤ 200K state variables) uses SuperLU_MT for direct Jacobian factorization. On moderate grids, SuperLU's memory requirements exceed available memory:

- 64×64 × 9 slots = 36,864 unknowns → SuperLU needs 15M+ entries → crash
- 32×32 × 9 slots = 9,216 unknowns → SuperLU needs 3.78M entries → crash
- 16×16 × 9 slots = 2,304 unknowns → works

This means multi-field systems (6+ fields with 9 state slots) on grids larger than ~20×20 cannot use the sparse tier, even though IDA is required for DAE constraint enforcement.

**Workaround applied:** massive_gravity example reduced to 16×16 grid (commit pending).

**Root cause:** Commit 7f3df3e disabled the analytical Jacobian GMRES tier for the sparse tier because it caused IDACalcIC regression. This left a gap: systems too large for SuperLU but below the GMRES threshold (200K) have no viable linear solver.

**Proposed solutions (in order of preference):**

1. **Fix GMRES + IDACalcIC interaction:** Investigate why the analytical Jacobian GMRES path breaks IDACalcIC in the sparse tier. If the issue is specific to the IC phase, use SuperLU for IDACalcIC and switch to GMRES for time-stepping.
2. **Memory-based fallback:** Instead of pure size thresholds, estimate SuperLU memory requirements (`nnz * 8 bytes * fill_ratio`) and fall back to GMRES when estimated memory exceeds a configurable limit.
3. **Hybrid approach:** Use SuperLU for the constraint IC solve (small system, one-shot) and GMRES for the time-stepping Jacobian (iterative, memory-efficient).
4. **Lower GMRES threshold:** Reduce `SPARSE_THRESHOLD` from 200K, but requires validating GMRES convergence on smaller systems.

**Relevant code:**

- `tidal/solver/_types.py:34` — `DENSE_THRESHOLD = 2_000`, `SPARSE_THRESHOLD = 200_000`
- `tidal/solver/ida.py` — linear solver selection logic
- `tidal/solver/analytical_jacobian.py` — GMRES tier (currently restricted to N > SPARSE_THRESHOLD)
- Commit 7f3df3e — disabled analytical Jacobian for dense tier to prevent IDACalcIC regression
