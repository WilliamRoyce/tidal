## Hard design rules (user directives — not negotiable)

1. **The existing framework is legacy, not a template.** It is acknowledged as naive and
   gradually patched-on. Design the ideal package for the goal from first principles;
   consult old code only for physics content and as test oracles.
2. **New code never imports old code.** No adapters, no shims. Useful capabilities are
   **fully ported**: redesigned to fit the new architecture, moved over with their
   docstrings, why-comments, and GitHub-issue references traveling along, and reviewed
   against the original as test oracle. The old copy stays in place, functional,
   untouched.
3. **Two fully separated packages/CLIs during the transition.** The new package gets its
   own entry point; the legacy `tidal` CLI stays as-is for cross-checking against
   thesis-era behavior. Never mixed. Legacy is retired deliberately once the new package
   demonstrably covers a role — never two live implementations presented for one job.
4. The goal shape: a **Cobaya extension** — a `Theory` class chaining off latest upstream
   CAMB (`{"CAMBdata": None}` → `provider.get_CAMBdata()`), plain dotted-path YAML
   reference (no entry-point registration), defaults in a `[ClassName].yaml` beside the
   module. Best packaging template found so far: `simonsobs/cosmopower_cobaya`.

## Known facts about the legacy layering (from the planning audit)

`tidal/cli/` is 25,566 of ~67k lines and holds the forward model (`_simulate` 3,085
lines; `run_inference_step` and `_measure_from_sim_data` in `_sweep.py`).
`tidal/inference/_likelihood.py` (5 sites), `tidal/measurement/_posthoc_audit.py`,
`tidal/inference/_prior_stability.py`, `tidal/measurement/_sweep_results.py` all import
*private* functions back out of the CLI package, each suppressed with
`# pyright: ignore[reportPrivateUsage]` or `# noqa: PLC0415`. The forward model takes an
`argparse.Namespace` because the CLI *is* the config object;
`_backfill_simulate_args` (`tidal/measurement/_posthoc_audit.py:278-318`) documents the
~20 attributes it needs — useful as a *requirements list* for the new config design, not
as a shim to build on.

## Task

1. **Design the target package** from the Cobaya-extension goal backwards: package
   name/namespace (decide and justify: under `tidal.*` vs a fresh top-level name — flag
   this prominently, the user wants to weigh in), module layout, public API, config
   objects, where the Cobaya `Theory`/likelihood components live, where the WS3 solver
   lives, where the WS6 spectrum module lives, test layout, docs layout, packaging
   (`pyproject`, optional extras: `cobaya`, `camb`).
2. **Decide the fate of `tidal/inference/`** under D9 (Cobaya supplies priors, samplers
   incl. PolyChord, output): which capabilities are worth re-implementing in the new
   structure (candidates: the cubed-sphere joint prior `RadialAngularPrior`; the
   `_importance.py` KL/BMD diagnostics — could become Cobaya-compatible components or
   post-processing tools), and what is retired as redundant.
3. **Port inventory**: enumerate the legacy capabilities the new package will eventually
   need (symbolic pipeline interface, coefficient evaluation concepts, operator kernels,
   measurement algorithms, validity-flag machinery), and for each: port / re-implement
   informed-by / not needed. With the documentation-preservation requirement stated per
   item.
4. **Migration order** consistent with the workstream order (WS2 ∥ WS3 → WS4 → WS5) and
   the observable ladder (O0/O1 first — so the Cobaya wiring and tabulated-background
   feature come early).
5. **CI/test strategy** for two coexisting packages (legacy suite untouched and green;
   new suite grows; cross-check tests that compare new against legacy where they overlap).
