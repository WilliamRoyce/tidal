## Why this exists

The new package's two upstream design decisions are open, and both prompts that would build
on them were about to be written against assumptions nobody had checked:

- **D-A — how Python drives Wolfram at derivation time.** `stage1_engineering_plan.md:502-530`
  prescribes Python text-templating a standalone `.wls` script modeled on legacy
  (`tidal/cli/_derive.py::{_wls_fields,_wls_lagrangian}`), plus one committed exporter package
  (`:567-570`). No document weighs the alternatives: a committed Wolfram **package that
  receives data**, or a **`wolframclient` session** calling that package directly from Python
  (the `wolfram` extra in `pyproject.toml` already declares `wolframclient`). Legacy's
  generated-code failure modes ("parenthesize multiline Lagrangians", "constants must not
  contain underscores") are what you get when the generator does not understand the language
  it emits.
- **D-B — what a user writes, and how the derived artifact reaches the Cobaya Theory.**
  Sampling-time configuration is *already decided, by Cobaya itself*: a user writes
  `theory: {tidal.SpectatorTheory: {...}}` and a component's defaults live in
  `<ClassName>.yaml` beside the class (`repo_reshape.md:509-511,554-559,652-657`); a
  `CobayaComponent` receives its whole YAML block as attributes (verified in the installed
  cobaya 3.6.2, `component.py`). But **the contents of that block are written nowhere, and
  neither is how the derived artifact (the spec / WXF the Wolfram stage produces) reaches the
  Theory** — by path, embedded, discovered. Where M3 even writes derived specs is explicitly
  undecided (`repo_reshape.md:1011-1016`). Legacy's TOML input exists only by inheritance
  (`tidalcosmo/derive/README.md:12`) and **carries no weight**: the interface is to be designed
  from what CAMB/Cobaya users already do.
- **Convention carriage.** PSALTer and CAMB each use a fixed, different Minkowski signature.
  Which terms of an abstract-index quadratic Lagrangian carry a minus sign depends on it;
  physics and equations of motion agree either way, but PSALTer judges the *health* of modes,
  and `spectrum_design.md:204-207` records that "the parity factor in every ghost verdict is
  *defined by* the signature". A silent sign slip between conventions could flip a ghost
  verdict. #513 forbids a translation layer. **The signature is not something the user
  declares** — the user writes one Lagrangian in one documented convention; the pipeline maps
  it deterministically into each backend's fixed convention and asserts. Which convention the
  user writes in, how the mapping works, and what check catches a slip are yours to determine
  from source.

These are one path — user input → derivation → artifact → Cobaya — so they are one memo.

**Acceptance criterion for every option you propose:** a Cobaya user adds our theory the way
they add any theory — a block in the YAML they already have — and never learns a second file
format unless the derivation step genuinely needs one, in which case you say why the same YAML
cannot carry it. **A Cobaya run must never be able to start a Wolfram kernel.**

## What you produce

`docs/cosmology/interfaces_decision.md` — a decision memo, ≤ ~500 lines: options, evidence,
a recommendation for D-A and for D-B, the convention-carriage rule and its check, the
never-derive-in-a-sampler mechanism, and where M3 should write derived specs. **Evidence, not
argument**: every claim about a comparable is a citation to a fetched file, and every claim
about feasibility is a prototype you ran.

### Method

*Install each comparable that installs and run its own getting-started example; quote its
user-facing input verbatim* — never a paraphrase. Where a package has no code, read the
paper's supplementary code (TorC's was decisive for this programme before). Commit fetch
routes under `scripts/research/interfaces/`; payloads go under the gitignored `third_party/`
(the rule in `scripts/research/psalter_stage1/README.md`).

### Evidence to gather — five groups

1. **Cosmology ecosystem, installed and run.** hi_class, EFTCAMB, SymBoltz.jl, DISCO-EB,
   cosmopower_cobaya, SOLikeT, CLASS and CAMB native conventions, Cobaya's own
   `packages_path` / `python_path` / `renames` mechanisms, and TorC's supplementary Cobaya
   inputs (Zenodo 10.5281/zenodo.15866507). For each: (i) where the user writes the model and
   in what format; (ii) how a precomputed or derived artifact reaches the sampler — path in
   YAML, `packages_path` install, embedded, computed at `initialize()`; (iii) how staleness is
   detected; (iv) whether a sampler run can trigger heavy precompute; (v) license and
   maintenance state.
2. **Wolfram-side conventions.** How PSALTer's author supplies a theory (`Models/*.m`,
   `ParticleSpectrographCTEG.m` in the pinned supplementary materials); xAct package structure
   (`BeginPackage`, `Sources/`; xTras, xPert, and xPand's driver style — xPand is not installed,
   read its manual and paper); the Wolfram Client Library for Python (`wolframclient`:
   `WolframLanguageSession` evaluates a committed package's functions directly — no script
   generation at all).
3. **Other symbolic → numeric scientific pipelines.** FeynRules → UFO → MadGraph (model file
   in, generated code out), SARAH / SPheno, CppTransport / PyTransport (symbolic core → generated
   C++), Cadabra, `sympy` code generation. For each: what it generates versus what it passes as
   data, and what broke for them.
4. **Legacy's own record.** The generator functions above, one generated `.wls`, and the
   failure modes catalogued; the two-branch requirement (`spectrum_design.md:346-366`: two
   derivations from one input, sharing only the convention-free input model).
5. **Convention carriage, from source.** PSALTer's signature and `ε₀₁₂₃` (its `Sources/`, the
   `conventions` block its exports carry) and CAMB's (`camb.symbolic`, the Fortran); which
   terms of an abstract-index quadratic Lagrangian change sign between them; where a slip
   would change a ghost verdict; **which convention the user should write in** (the
   sign-sensitive spectrum branch makes PSALTer's the natural candidate — test that claim); how
   the pipeline maps into each backend without a translation layer (#513); the check that
   catches a slip.

### Prototypes — required

(a) **Three Wolfram shapes on the Vector theory**, each run once (template:
`scripts/psalter/vector_smoke.wls`, ~27 s): a Python-templated standalone `.wls`; a committed
package exposing `RunStage1[<|"fields" → …, "couplings" → …, "terms" → …|>]` driven by a

**All three must yield an identical `WaveOperator`.** Tabulate: lines of templating vs data
handling; testability (golden-text diffs vs `tests/wolfram/`-style unit tests); error
signalling — where the Wolfram-side `Catch` + `Exit[1]` that #561 deferred naturally lives
under each shape (an uncaught `Throw` exits `wolframscript` with status 0); how
`derivation_hash` is computed under each; readability for a Wolfram-literate physicist.

(b) **A ≤ 40-line Cobaya prototype** (`get_model` + `logposterior`, no CAMB) proving the
never-derive-in-a-sampler mechanism you recommend — refusal at `initialize()` on a missing
artifact, or on a content-hash mismatch between the artifact and the theory block — shown
**refusing and then passing**. Both transcripts go in the memo.

### Options — at least two, end to end

Each option is one path from what the user writes to what the Theory loads, with a worked YAML
for our case. **One of them must be the user's candidate: a single YAML whose `theory:`
sub-block is read by both `tidalcosmo derive` and Cobaya** — the derivation CLI reads only its
sub-block; Cobaya hands the same block to the Theory, which loads the artifact. A trade-off
table across: user learning cost, staleness safety, provenance of the artifact, testability,
what M3 must write and where, and what each implies for I-S1B's exporter
(`stage1_engineering_plan.md:565-570`).

## Working rules

- Worktree off `feat/cosmology-program`: `git worktree add /tmp/tidal-r1 -b cosmo/r1-interfaces feat/cosmology-program`. **Never merge.** Never touch the shared working directory.
- **Never version-bump, tag, or edit the changelog.** The orchestrator bumps once per wave.
- **Open a draft PR into `feat/cosmology-program` at your first commit** and report its number — a branch with no PR is never seen by CI, and CI is the gate (local `cspell` is a pre-check only; the action's dictionary differs).
- Stay inside your owned paths.
- **Assertions get verified before they land; hypotheses do not have to be.** A claim you write into the memo as settled is one the next session will act on. A hypothesis with its test named beside it costs one command when wrong.
- **An argument for why something cannot be checked is not evidence about how the check comes out.** If a shape cannot be prototyped here, say so and stop — do not also predict the result.
- **A caveat that is a scope limit hides better than a doubt.** "I could not test X in this environment" must reach the memo's option table, not only your report.
- **Read the tool's own known-issues before hypothesizing.** PSALTer's README, `wolframclient`'s issue tracker, Cobaya's docs on component options.
- **Reduce before you bisect.** The Vector theory (27 s) is the instrument; never CTEG (7 min).
- One `wolframscript` at a time, machine-wide. The lane guard (`.claude/hooks/wolfram-guard.sh`) blocks a second kernel, including through wrapper scripts.
- No environment-specific absolute paths in anything committed (`tests/test_repo_hygiene.py` rejects `/workspaces/`, `/home/<user>/`, the Claude project slug).
- Conventional commits; American English; no attribution trailers.

## If you find the design wrong

A design-document contradiction or error: amend it **at the instruction site**, pinned to the
version, and report it — do not work around it silently. An architectural contradiction (the
design cannot be built as specified): **stop and report**; do not redesign in a delegate
session.
